Third-Party API Integration Service

The problem

Calling an external API directly from business code spreads provider-specific details everywhere. When the provider is slow or returns an error, failures are hard to trace and can cascade into the rest of the application.

Proposed solution

A dedicated ASP.NET Core Web API that owns the integration: it validates incoming requests, calls the provider through a typed HttpClient with timeouts and retry policies, maps responses to an internal contract and records each exchange for diagnosis.

Architecture

  1. Client application
  2. Integration API (validation)
  3. Typed HttpClient + resilience policies
  4. External REST provider (public sandbox)
  5. SQL Server request log

Main features

  • Request validation with clear problem-details error responses
  • API-key or token authentication; secrets loaded from configuration / user secrets, never committed
  • Timeouts, retries with back-off and a circuit breaker for transient failures
  • Structured logging with correlation IDs across the request
  • Persistence of requests, responses and status for auditing and replay
  • Integration tests against a mocked provider

Technology

  • ASP.NET Core Web API
  • C#
  • HttpClientFactory
  • SQL Server

Status: planned / in development. The demo will integrate with a free public API, not with any employer or client system.

Sample project Case study

SQL Server Performance Toolkit

The problem

Slow queries are usually discussed in the abstract. Developers rarely get a safe place to see a bad execution plan, change one thing, and measure the difference on realistic data volumes.

Proposed solution

A public repository of self-contained scenarios. Each one includes a script that generates test data, a deliberately slow query, an explanation of the execution plan, and one or more improved versions — so results can be reproduced on any SQL Server instance.

Workflow for each scenario

  1. Generate test data
  2. Run baseline query
  3. Read execution plan & I/O stats
  4. Apply one change
  5. Re-measure & document

Planned scenarios

  • Diagnosing a slow query with actual execution plans and SET STATISTICS IO, TIME
  • Missing and unused index analysis
  • Non-sargable predicates and implicit conversions
  • Parameter sniffing in stored procedures
  • Rewriting cursor-based procedures as set-based T-SQL

Technology

  • SQL Server
  • T-SQL
  • Execution plans
  • Indexing

Status: planned / in development. Benchmark numbers will only be published alongside the scripts used to produce them, with hardware and data volume stated.

Sample project Case study

Analytics Tracking Demonstration

The problem

Many sites have analytics installed but cannot trust the numbers: events fire twice, conversions are not tracked, and nobody has written down what each event means.

Proposed solution

A small demo storefront with a written tracking plan. Every event is pushed to the data layer, configured in Google Tag Manager, sent to a GA4 test property, and verified using GTM Preview and GA4 DebugView.

Event flow

  1. User action
  2. dataLayer.push()
  3. GTM trigger & tag
  4. GA4 test property
  5. DebugView validation

Main features

  • Page-view tracking, including single-page navigation
  • Form-submission and lead (generate_lead) events
  • Simulated e-commerce funnel ending in a purchase event with test data
  • Consent-aware loading of tags
  • A tracking-plan document describing every event and parameter
  • Optional: forwarding events through a server-side tagging container

Technology

  • JavaScript
  • Google Analytics 4
  • Google Tag Manager

Status: planned / in development. Uses a separate test GA4 property; no real customer or purchase data.
